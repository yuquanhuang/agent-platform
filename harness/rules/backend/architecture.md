# Python Backend Architecture Rules

## 先服从项目真实架构

- 编码前先读取现有目录、依赖方向、入口、配置和测试，禁止仅根据模板猜测项目结构。
- `harness/project.json` 只描述路径和质量命令，不替代项目架构文档。
- 历史代码不满足规则时，仅在需求触及范围内渐进治理。

## 推荐边界

无论项目采用传统分层、六边形架构还是领域驱动设计，都应明确以下职责：

- 接口层：协议解析、参数校验、鉴权入口和响应映射。
- 应用层：用例编排、事务边界和跨组件协作。
- 领域层：业务规则和领域数据表达，不依赖具体传输协议。
- 基础设施层：数据库、缓存、消息、文件和外部服务适配。
- 后台任务入口：只负责触发和上下文准备，复杂业务委托给应用层。
- 通用工具：只放无业务状态、可复用的技术能力。

## 依赖约束

- 接口入口不得直接堆积 SQL、事务和跨系统编排。
- 领域模型不得依赖 HTTP 路由、数据库会话或具体外部客户端。
- 基础设施实现不得反向调用接口层。
- 禁止通过循环导入或随意移动导入位置掩盖错误的依赖方向。
- 所有外部访问通过明确的 repository、client、gateway 或 adapter 边界封装。

## 异步、事务和任务

- `async def` 调用链中不得直接执行已知阻塞 I/O。
- 数据库事务必须有明确所有者，提交、回滚和资源释放不得跨层隐式发生。
- 并发任务必须设置并发度、超时、取消和失败收敛策略。
- 消息处理和可重试任务必须评估幂等、重复消费和部分失败。
